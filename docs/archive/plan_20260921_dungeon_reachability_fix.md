# Implementation Plan: Phase 41 - Dungeon Reachability Guarantees

## 1. Task Overview
手続き生成されたフロアが「進行不能」になるケースを潰します。現在、鍵扉を含むフロアの約11%で階段にも鍵にも到達できず、そのフロアを攻略できません。あわせて商人タイルが通路を恒久的に塞ぐ問題を修正し、これらを回帰させないテストを追加します。

主目的:
- 鍵チェストを必ず「鍵を持たない状態で到達できる位置」に配置する。
- 商人タイルが階段への唯一の経路を塞がないようにする。
- 到達性の不変条件をテストで固定し、生成アルゴリズムを今後変更しても破綻を検出できるようにする。

本フェーズはダンジョン生成の**配置制約のみ**を変更します。部屋・通路の生成アルゴリズム、罠・泉・宝箱の出現率、戦闘やアイテムの仕様は変更しません。

## 2. 背景（調査結果）

### 2.1 鍵チェストが鍵扉の内側に生成される
`logic/map_generator.py` の鍵チェスト配置は、部屋の中心タイルが壁／鍵扉でないことしか確認しておらず、**到達可能性を検査していません**。

```python
if doors_placed > 0 and len(rooms) >= 2:
    for r in rooms[1:]:
        kx = r[0] + r[2] // 2
        ky = r[1] + r[3] // 2
        if tiles[ky][kx] not in (TILE_WALL, TILE_LOCKED_DOOR):
            tiles[ky][kx] = TILE_CHEST
            m.key_chest_pos = (kx, ky)
            break
```

`dungeon_key` の入手経路は `main.py` の `_open_chest()` 内、`key_chest_pos` に一致した宝箱のみです。`SHOP_KEYS` / `MERCHANT_KEYS` / `_DROP_TIERS` のいずれにも含まれていないため、鍵チェストが扉の内側に出た時点でそのフロアの鍵は入手不能になります。

B3F以降を3,102フロア生成した実測（鍵扉を通行不能として flood fill）:

| 状態 | 件数 | 鍵扉フロアに対する割合 |
| :--- | ---: | ---: |
| 鍵扉のあるフロア | 3,102 | - |
| └ 鍵チェストが扉の内側 | 465 | 15.0% |
| 　└ かつ階段も扉の内側 | **347** | **11.2%** |

最下段が実害です。`T` キーで街には戻れますが、`_enter_dungeon_fresh()` は `dungeon_floor = 1` にリセットするため、潜行中の進行が失われます。

再現例（いずれも `current_floor=3`）: `random.seed(189)` / `random.seed(1026)` / `random.seed(1088)`
（`seed * 31 + floor` で seed=6, 33, 35 に相当）

### 2.2 商人タイルが通路を恒久的に塞ぐ
`_interact_fountain()` は泉タイルを `set_tile(nx, ny, TILE_FLOOR)` で床に変換しますが、`_interact_merchant()` は**タイルを変換しません**。`Map.is_wall()` は `TILE_MERCHANT` を通行不能として扱うため、幅1の通路に商人が出ると恒久的な壁になります。

実測では、商人を含む616フロア中**19フロア**で商人が階段への唯一の経路を塞いでいました。泉は接触時に床へ変わるため同じ問題を起こしません。

### 2.3 既存テストが緩い理由
`tests/test_map_generator.py` の `reachable_tiles()` は `TILE_WALL` のみを通行不能としています。これは**階段の到達性**には正しい基準です（扉は鍵で開けられるため）。しかし**鍵チェストの到達性**には不適切で、「鍵を取る前でも鍵チェストへ行ける」ことを検証できていません。Phase 40 の指示書が「鍵扉は通過可能とみなす」と一律に指定したのが誤りでした。

## 3. Target Files

- `/workspaces/games/tests/test_map_generator.py`: 判定基準を2種類に分け、回帰テストを追加する。

## 4. Sub-Phases & Instructions

### Phase 41.1: 到達性ヘルパーの追加
1. **`logic/map_generator.py` にモジュール内ヘルパーを追加**:
   - シグネチャ例: `def _reachable(tiles, width, height, start, blocked):`
   - `start` から4方向のBFS/DFSで到達できる座標の `set` を返す。`blocked` は通行不能タイルの集合（`frozenset`）として受け取る。
   - 盤面が20x20（400マス）なので素朴なBFSで十分。最適化は不要。
   - `Map` のメソッドにはせず、生成中の生タイル配列に対して使えるモジュール関数にする。`Map.is_wall()` とは判定基準が異なるため、既存メソッドを流用しないこと。
2. **判定基準の定数化**:
   - `_BLOCK_WALL = frozenset({TILE_WALL})`: 鍵入手後に通れる範囲。
   - `_BLOCK_NO_KEY = frozenset({TILE_WALL, TILE_LOCKED_DOOR})`: 鍵を持たない状態で通れる範囲。
   - 泉は接触時に床へ変わるため、どちらにも含めない。

### Phase 41.2: 鍵チェスト配置の修正
1. **到達可能な部屋に限定する**:
   - 鍵扉を配置した後に `reachable = _reachable(tiles, width, height, (m.start_x, m.start_y), _BLOCK_NO_KEY)` を計算する。
   - `rooms[1:]` を走査し、中心が `reachable` に含まれ、かつタイルが `TILE_WALL` / `TILE_LOCKED_DOOR` / `TILE_STAIRS` のいずれでもない部屋を選ぶ。
   - **`TILE_STAIRS` の除外を必ず入れること**。現状は除外がなく、`len(rooms) == 2` のとき `rooms[1]` が階段のある `rooms[-1]` と一致して階段を宝箱で上書きし得る。3,200フロアの実測では発生しませんでしたが、潜在的な不具合なのでここで塞ぐ。
2. **部屋の中心が使えない場合のフォールバック**:
   - どの部屋の中心も条件を満たさない場合、`reachable` に含まれる `TILE_FLOOR` のタイル（開始地点と階段を除く）から1つ選んで鍵チェストにする。
   - 候補選択は `random.choice` ではなく決定的な順序（走査順の先頭）でもよい。ただし乱数を使う場合は、既存の乱数消費順序を変えると同一seedでのマップが変わる点に注意する（テストのseed固定値を更新する必要が出る）。
3. **最終フォールバック: 扉を撤去する**:
   - それでも配置先が無い場合、**配置済みの鍵扉をすべて `TILE_FLOOR` に戻し**、`m.key_chest_pos = None` とする。
   - 「鍵の入手手段が無いフロアには鍵扉を置かない」を最終的な不変条件とする。扉を残したまま鍵を配置できない状態で抜けないこと。

### Phase 41.3: 商人配置の修正
1. **配置候補の検証**:
   - 商人タイルを仮配置し、`_reachable(..., blocked=_BLOCK_WALL | {TILE_MERCHANT})` で階段が到達可能かを確認する。
   - 到達不能になる候補は採用せず、次の候補へ進む。全候補が不適格なら商人を配置しない（商人は20%確率の任意要素なので、出現しなくても問題ない）。
2. **鍵チェストとの整合**:
   - 商人が鍵チェストへの経路を塞がないことも同時に確認する。`key_chest_pos` が設定済みの場合は、階段と同じ基準で到達性を確認する。
   - 実装順序に注意: 現在のコードは「鍵扉 → 鍵チェスト → 泉 → 商人」の順に配置している。商人の検証は鍵チェスト確定後に行うため、この順序のままでよい。
3. **泉は対象外**:
   - `_interact_fountain()` がタイルを床へ変換するため、泉は恒久的な障害にならない。泉の配置ロジックは変更しない。
4. **`_interact_merchant()` は変更しない**:
   - タイルを床に変換する案もあるが、商人が初回接触で消えるゲーム仕様変更になる。本フェーズでは配置側の制約のみで解決する。

### Phase 41.4: テストの厳格化
1. **`reachable_tiles()` に判定基準の引数を追加**:
   ```python
   def reachable_tiles(dungeon_map, blocked=(TILE_WALL,)):
   ```
   - 既定値は現状どおり `TILE_WALL` のみ。呼び出し側で基準を明示する。
2. **階段の到達性（基準: `TILE_WALL` のみ）**:
   - 既存の `test_generated_maps_preserve_floor_invariants` はこの基準のままでよい。扉は鍵で開けられるため通過可能とみなすのが正しい。
3. **鍵チェストの到達性（基準: `TILE_WALL` + `TILE_LOCKED_DOOR`）**:
   - `test_key_chest_is_reachable_when_a_locked_door_is_generated` を、鍵扉を通行不能とした基準へ変更する。
   - 検証内容: 鍵扉が存在するフロアでは `key_chest_pos` が `None` でなく、そのタイルが `TILE_CHEST` で、**鍵を持たない状態で到達可能**であること。
   - Phase 41.2 の最終フォールバックを考慮し、「鍵扉が存在するなら鍵チェストも到達可能」という含意の形で書く。扉が撤去されたフロアはこの検証をスキップしてよい。
4. **商人の非遮断性**:
   - 商人が存在するフロアで、`TILE_WALL` と `TILE_MERCHANT` を通行不能としたとき、階段が到達可能であることを検証する新規テストを追加する。
5. **seed の範囲**:
   - 鍵扉はB3F以降にしか出ないため、`current_floor=3` 以上で生成すること。
   - 不具合は鍵扉フロアの約15%で発生していたため、seed 20件程度では検出漏れが起きる。**最低100 seed**は回すこと（現行テストは100 seedで回しており、実行時間は全体で0.2秒程度なので余裕がある）。
   - 商人は出現率20%と低いため、商人テストはより広く回すか、複数フロアを対象にすること。

### Phase 41.5: ドキュメント同期
1. **仕様詳細更新**:
   - `docs/3. 仕様詳細.md` の鍵扉・鍵チェスト・商人の項に、以下を不変条件として明記する。
     - 鍵チェストは、鍵を持たない状態で開始地点から到達できる位置にのみ配置される。
     - 上記を満たせない場合、そのフロアに鍵扉は配置されない。
     - 商人は、階段および鍵チェストへの唯一の経路を塞ぐ位置には配置されない。
     - 泉は接触時に床へ変換されるため、経路を塞がない。
2. **開発タスク更新**:
   - `docs/4. 開発タスク.md` に Phase 41 を追加し、41.1〜41.4 の完了チェック欄を作る。
3. **完了処理**:
   - 実装と確認が完了したら、本指示書を `docs/archive/plan_20260921_dungeon_reachability_fix.md` へ移動する。

## 5. Constraints
- **実装を先、テストを後**: Phase 41.2 / 41.3 の生成器修正を済ませてから Phase 41.4 のテスト厳格化を行う。逆順にするとCIが赤くなる。
- **生成アルゴリズムの骨格を変えない**: 部屋数（25回試行）、部屋サイズ、通路の引き方、罠・泉・宝箱の出現率は変更しない。本フェーズは配置先の制約追加のみ。
- **乱数消費順序への注意**: 候補選択に `random` を追加・削除するとseedごとの生成結果が変わる。既存テストのseed期待値に影響しないか確認すること。可能なら乱数を追加消費しない実装を選ぶ。
- **`Map.is_wall()` を到達判定に流用しない**: 同メソッドは泉と商人も壁扱いにしており、泉が床へ変換される挙動を反映していない。到達判定には Phase 41.1 の専用ヘルパーを使う。
- **ASCII制約**: ゲーム内表示文字列はASCIIのみ。本フェーズで新規のゲーム内文字列は追加しない想定。
- **Pyxel色制約**: 色番号は0〜15のみ（本フェーズで描画コードは変更しない）。
- **pyxel非依存を維持**: `logic/map_generator.py` に pyxel を import しないこと。CIのtestジョブがディスプレイ無しで動く前提が崩れる。

## 6. Success Criteria
1. B3F以降を1,000フロア以上生成して、鍵扉が存在するすべてのフロアで、鍵扉を通行不能とした場合でも `key_chest_pos` に到達できる。
2. 鍵扉を配置できなかった（または撤去した）フロアでは `key_chest_pos` が `None` で、鍵扉タイルも残っていない。
3. 階段を宝箱で上書きしてしまうケースが無く、全フロアで階段がちょうど1つ存在する。
4. 商人が存在するフロアで、商人を通行不能としても階段へ到達できる。
5. `pytest` が全件成功し、鍵チェスト・商人の各テストが**修正前のコードでは落ちる**ことを確認済みである（テストが実際に不具合を捕まえられることの確認）。
6. `docs/3. 仕様詳細.md` と `docs/4. 開発タスク.md` が実装内容と一致している。

## 7. Recommended Verification
1. `pytest` を実行し、全件成功することを確認する。
2. **修正前のコードに新テストだけを当てて、落ちることを確認する**（`git stash` で生成器の修正のみ退避するなど）。落ちない場合はテストが不十分。
3. 調査に使った検証を再実行し、`key chest behind a locked door` が 0 件になることを確認する。B3F〜B10Fを各400 seed、計3,200フロア程度。
4. 再現例のseedを個別に確認する: `current_floor=3` で `random.seed(189)` / `random.seed(1026)` / `random.seed(1088)`。修正前は階段・鍵チェストともに扉の内側、修正後はいずれかが到達可能になっていること。
5. `python main.py` を起動し、B3F以降で鍵扉に遭遇したフロアで実際に鍵を入手して扉を開けられることを確認する。
6. 商人が出たフロアで、商人の周囲を通行して階段へ到達できることを確認する。
